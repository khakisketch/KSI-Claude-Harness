# Review Core — 변경 전체 검토 기준

> **출처:** [obra/superpowers](https://github.com/obra/superpowers) `skills/requesting-code-review/code-reviewer.md`
> commit `3cd2db9f8aa48cf7907c55adfaef2db540702209` (2026-06-16) 에서 검토 기준을 가져와 이 하네스에 맞게 고쳤다.
> **고친 것 3가지:** ① 원문은 `git diff`·`git worktree add`를 직접 실행하라고 하지만 우리 `reviewer`는
> **Bash가 없다**(구조적 read-only) — 위임자가 diff를 주거나 파일을 Read한다. ② severity 어휘를
> Critical/Important/Minor → 우리 **critical/high/medium/low**로. ③ 판정 어휘를 "Ready to merge?" →
> `release-risk` 스킬이 이미 쓰는 **Approved / Needs changes / Blocked**로(새 어휘를 만들지 않는다).

## 입력으로 받아야 할 것

이게 없으면 검토가 아니라 추측이다. 없으면 **없다고 보고하고 요청**한다.

- **수용기준 또는 계획** — 무엇을 하기로 했나
- **최종 diff** — 무엇이 바뀌었나 (Bash가 없으므로 위임자가 준다)
- 관련 계약·스키마 — API 시그니처·DB 스키마·설정
- 기계 검증 결과 — lint/typecheck/test가 무엇을 통과했고 무엇을 안 돌렸나

**받지 말아야 할 것:** 구현자가 왜 그렇게 했는지에 대한 긴 설명, "문제없다"는 결론.
그걸 읽으면 그 논리에 끌려가 반증이 죽는다.

## 5축

**요구사항 정합**
- 구현이 계획·수용기준과 맞나
- 벗어난 부분이 있으면 그건 정당한 개선인가, 문제 있는 이탈인가
- 계획된 기능이 전부 있나

**코드 품질**
- 관심사 분리 · 에러 처리 · 타입 안전성
- 성급한 추상화 없이 중복 제거됐나
- 엣지 케이스가 처리됐나

**아키텍처**
- 설계 판단이 타당한가 · 확장성·성능 · 보안
- 주변 코드와 깔끔하게 붙나

**테스트**
- 테스트가 **mock이 아니라 실제 동작**을 검증하나
- 엣지 케이스가 덮였나 · 필요한 곳에 통합 테스트가 있나
- 전부 통과했나 (자기보고가 아니라 실제 출력으로)

**프로덕션 준비도**
- 스키마가 바뀌었으면 마이그레이션 전략이 있나
- 하위 호환이 고려됐나 · 문서 · 명백한 버그

## 보정 — 전부 critical이 아니다

실제 심각도로 분류한다. nitpick을 critical로 올리면 진짜 critical이 묻힌다.
**잘된 것을 먼저 짚는다** — 정확한 칭찬이 있어야 나머지 지적이 신뢰받는다.
계획 자체에 문제가 있으면 구현이 아니라 계획을 지적한다.

## 출력

```
### 잘된 것
[구체적으로. 파일:라인]

### 이슈
#### critical — 반드시 고친다
[버그 · 보안 · 데이터 손실 위험 · 기능 파손]
#### high — 고쳐야 한다
[아키텍처 문제 · 누락된 기능 · 부실한 에러 처리 · 테스트 공백]
#### medium / low — 개선 여지
[코드 스타일 · 최적화 기회 · 문서 다듬기]

각 이슈마다: 파일:라인 · 무엇이 잘못됐나 · 왜 문제인가 · 어떻게 고치나(자명하지 않으면)

### 권고
[코드 품질·아키텍처·프로세스 개선]

### 판정
**Approved / Needs changes / Blocked** + 1~2문장 근거
검증하지 못한 축이 있으면 여기에 **명시**한다(예: "테스트 축 미검증 — 실행 결과 미제공").
```

## 규칙

**한다:** 실제 심각도로 분류 · 파일:라인으로 구체적으로 · 왜 문제인지 설명 · 잘된 것 인정 · 명확한 판정.

**안 한다:** 안 보고 "괜찮아 보인다" · nitpick을 critical로 · **읽지 않은 코드에 대한 피드백** ·
"에러 처리를 개선하라" 같은 모호한 말 · 판정 회피.

**고치지 않는다** — 결함을 찾으면 위치·근거·재현법만 보고한다(read-only는 tier 분리이지 제약이 아니다).
