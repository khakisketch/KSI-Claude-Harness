# Review Core — 변경 전체 검토 기준

## 입력

없으면 검토가 아니라 추측이다. 없으면 "없다"고 보고하고 요청한다.

**필요:**
- 수용기준 또는 계획
- 최종 diff(Bash 없음 — 위임자가 제공)
- 관련 계약·스키마 — API 시그니처·DB 스키마·설정
- 기계 검증 결과 — lint/typecheck/test 통과 여부, 무엇을 안 돌렸나

**받지 않는다:** 구현자의 설명, "문제없다"는 결론.

## 5축

**요구사항 정합**
- 구현이 계획·수용기준과 맞나
- 벗어난 부분이 있으면 정당한 개선인가, 문제 있는 이탈인가
- 계획된 기능이 전부 있나

**코드 품질**
- 관심사 분리 · 에러 처리 · 타입 안전성
- 성급한 추상화 없이 중복 제거됐나
- 엣지 케이스가 처리됐나

**아키텍처**
- 설계 판단이 타당한가 · 확장성·성능 · 보안
- 주변 코드와 깔끔하게 붙나

**테스트**
- 테스트가 mock이 아니라 실제 동작을 검증하나
- 엣지 케이스가 덮였나 · 필요한 곳에 통합 테스트가 있나
- 전부 통과했나(자기보고가 아니라 실제 출력으로)

**프로덕션 준비도**
- 스키마가 바뀌었으면 마이그레이션 전략이 있나
- 하위 호환이 고려됐나 · 문서 · 명백한 버그

계획 자체에 문제가 있으면 구현이 아니라 계획을 지적한다.

## 출력

```
### 잘된 것
[구체적으로. 파일:라인]

### 이슈
#### critical — 반드시 고친다
[버그 · 보안 · 데이터 손실 위험 · 기능 파손]
#### high — 고쳐야 한다
[아키텍처 문제 · 누락된 기능 · 부실한 에러 처리 · 테스트 공백]
#### medium / low — 개선 여지
[코드 스타일 · 최적화 기회 · 문서 다듬기]

각 이슈마다: 파일:라인 · 무엇이 잘못됐나 · 왜 문제인가 · 어떻게 고치나(자명하지 않으면)

### 권고
[코드 품질·아키텍처·프로세스 개선]

### 판정
**Approved / Needs changes / Blocked** + 1~2문장 근거
검증하지 못한 축이 있으면 여기에 명시한다(예: "테스트 축 미검증 — 실행 결과 미제공").
```

## 규칙

- 읽지 않은 코드에 대해 말하지 않는다 — 안 보고 "괜찮아 보인다"가 최악이다.
- **고치지 않는다** — 결함을 찾으면 위치·근거·재현법만 보고한다.
