# Debug — 추측을 멈추고 원인을 좁힌다

버그 하나마다 부르는 절차가 아니다. **추측-수정 루프에 빠졌을 때** 꺼내는 도구다.
원인을 모르고 넣은 수정은 고쳐도 왜 고쳐졌는지 모르고, 대개 다른 데서 다시 터진다.

빠진 걸 스스로 알아채기 어려워서(그래서 이 스킬은 60일간 0회 호출됐다) `debug-loop-nudge` 훅이
같은 파일 8회째 편집에서 밖에서 깨운다 — 임계값은 실측 p95다. 알림이 왔는데 원인을 알고 고치는
중이면 무시하고, 아니면 여기부터.

## 1. 재현부터

- 에러 메시지를 **끝까지** 읽는다(스택 중간을 건너뛰지 않는다). 대부분 여기서 끝난다.
- **일관되게 재현되는 최소 케이스**를 만든다. 재현이 들쭉날쭉하면 그것 자체가 단서다 — 시간·순서·캐시·동시성·환경 중 하나다.
- 최근에 뭐가 바뀌었나(`git log`·`git diff`). 어제 되던 게 오늘 안 되면 답은 대개 그 사이에 있다.

## 2. 데이터 흐름을 거꾸로 따라간다

- 잘못된 값이 **처음 나타나는 지점**까지 거슬러 올라간다. 터진 자리는 대개 원인이 아니다.
- 컴포넌트 경계(함수 진입·API 응답·DB 반환·직렬화 전후)에서 실제 값을 찍어 본다. 추측한 값 말고 실제 값.
- 되는 케이스가 있으면 **끝까지 비교**한다. "비슷한데 왜 저건 되지"에서 멈추지 말고 차이를 전부 나열한다.

## 3. 한 번에 한 변수

- 가설을 문장으로 적는다: "X가 Y라서 Z가 된다."
- **가장 싸게 그 가설만 반증하는 실험**을 한다. 여러 곳을 동시에 바꾸면 뭐가 고쳤는지 영영 모른다.
- 가설이 틀리면 폐기하고 다음으로. 맞을 때까지 실험을 늘리지 말고 가설을 바꾼다.

## 4. 고치고 나서

- **재현 케이스를 테스트로 남길지는 그때 판단한다** — 재발이 아프거나 계약이 확정된 자리면 남기고, 아직 모양이 바뀔 코드면 고치고 넘어간다. 여기서의 "먼저 실패하는 테스트"는 TDD 의식이 아니라 *이 버그가 진짜 고쳐졌나*를 재는 수단이다.
- 수정은 근본 원인 한 곳에. 방어 코드를 여기저기 뿌리는 건 원인을 못 찾았다는 신호다.
- 왜 고쳐졌는지 한 줄로 설명할 수 없으면 아직 안 고쳐진 것이다.

## 멈춰야 할 신호

- **세 번째 수정을 시도하고 있다** → 문제가 이 층이 아닐 수 있다. 설계·데이터 모델·라이브러리 선택을 의심하고 그걸 보고한다.
- 원인 설명 없이 "이러면 될 것 같다"로 고치고 있다 → 1번으로 돌아간다.
- 재현을 못 하는데 고치고 있다 → 고쳤는지 확인할 방법도 없다는 뜻이다.
